## A. Introduction

Database schema design turns the conceptual ER diagram into a concrete set of relational tables that PostgreSQL can create and enforce. For this project, the schema has three jobs:

1. **Store event data reliably**: users, venues, events, registrations and certificates, each in its own table with typed columns.
2. **Enforce integrity at the lowest level**: duplicate registrations, duplicate e-mails, invalid dates and orphan records are rejected by the database itself, not only by application code.
3. **Give the backend a stable contract**: the same design is expressed as SQL (`SEPM_Database_Schema.sql`) and as a Prisma schema (`schema.prisma`), so the Express API, Zod validation and the database all agree.

The schema has **exactly five tables** (`users`, `venues`, `events`, `registrations`, `certificates`) and **six relationships**, as in the ER diagram. No ROLE, PERMISSION, LOGIN or EVENT_SESSION table exists; `role` is a column of `users`, and event date/time columns live directly in `events`.

### Naming conventions

| Object | Convention | Example |
|---|---|---|
| Tables | lower-case plural snake_case | `registrations` |
| Columns | lower-case snake_case | `student_id_number` |
| Primary key | `pk_<table>` | `pk_users` |
| Foreign key | `fk_<table>_<meaning>` | `fk_events_organizer` |
| Unique | `uq_<table>_<column(s)>` | `uq_registrations_event_student` |
| Check | `chk_<table>_<rule>` | `chk_events_end_after_start` |
| Index | `idx_<table>_<column(s)>` | `idx_events_status_start_time` |
| Enum type | singular snake_case | `user_role` |

## B. Relational Schema

Notation: **PK** primary key · **FK** foreign key · **UK** unique key · *NULL* nullable column (all other columns are NOT NULL).

```text
USERS (
    id                  PK,
    name,
    email               UK,
    student_id_number   UK,
    password_hash,
    role                (STUDENT | ORGANIZER | ADMIN),
    department          NULL,
    created_at
)

VENUES (
    id                  PK,
    name                UK,
    location,
    capacity
)

EVENTS (
    id                  PK,
    title,
    description,
    organizer_id        FK -> USERS.id,
    venue_id            FK -> VENUES.id,
    start_time,
    end_time,
    registration_deadline,
    max_participants    NULL,
    status              (DRAFT | PUBLISHED | CANCELLED | COMPLETED),
    cancel_reason       NULL,
    created_at,
    updated_at
)

REGISTRATIONS (
    id                  PK,
    event_id            FK -> EVENTS.id,
    student_id          FK -> USERS.id,
    status              (REGISTERED | CANCELLED),
    certificate_eligible,
    registered_at,
    UNIQUE (event_id, student_id)        -- composite unique constraint
)

CERTIFICATES (
    id                  PK,
    registration_id     FK -> REGISTRATIONS.id, UK,
    certificate_no      UK,
    file_path,
    issued_at,
    issued_by           FK -> USERS.id
)
```

### Composite unique constraint

| Table | Constraint | Meaning |
|---|---|---|
| REGISTRATIONS | `UNIQUE (event_id, student_id)` | A student can have only one registration row per event, so duplicate registration is impossible. |

### Relationships implemented

| # | Relationship | Cardinality | Implemented by |
|---|---|---|---|
| 1 | USERS organizes EVENTS | 1 : 0..N | `events.organizer_id → users.id` |
| 2 | USERS makes REGISTRATIONS | 1 : 0..N | `registrations.student_id → users.id` |
| 3 | VENUES hosts EVENTS | 1 : 0..N | `events.venue_id → venues.id` |
| 4 | EVENTS receives REGISTRATIONS | 1 : 0..N | `registrations.event_id → events.id` |
| 5 | REGISTRATIONS earns CERTIFICATES | 1 : 0..1 | `certificates.registration_id → registrations.id` (**unique**) |
| 6 | USERS issues CERTIFICATES | 1 : 0..N | `certificates.issued_by → users.id` |

Because all foreign key columns are NOT NULL, the "one" side is mandatory on every relationship (for example, every event has exactly one organizer and one venue).

## C. Data Dictionary

Key column: **PK** primary key · **FK** foreign key · **UK** unique key. "—" means not applicable. All `id` columns are `GENERATED BY DEFAULT AS IDENTITY` (auto-increment).

### C.1 Table `users`

| Table | Column | PostgreSQL type | Size / precision | Key | Nullability | Default | Description and purpose |
|---|---|---|---|---|---|---|---|
| users | id | INTEGER | 4 bytes | PK | NOT NULL | identity (auto) | Unique identifier of each account; referenced by events, registrations and certificates. |
| users | name | VARCHAR(100) | 100 characters | — | NOT NULL | — | Full name, printed on certificates and shown in participant lists. |
| users | email | VARCHAR(255) | 255 characters | UK | NOT NULL | — | College e-mail used to log in. Stored in lower case (enforced by `chk_users_email_lowercase`) so uniqueness is case-insensitive in practice. |
| users | student_id_number | VARCHAR(30) | 30 characters | UK | NOT NULL | — | College ID card number. Text, not a number, because ID formats may contain letters or leading zeros. |
| users | password_hash | VARCHAR(255) | 255 characters | — | NOT NULL | — | bcrypt hash of the password (bcrypt output is 60 characters; 255 leaves room for future algorithms). The plain password is never stored. |
| users | role | user_role (ENUM) | 3 values | — | NOT NULL | `'STUDENT'` | Access level: STUDENT, ORGANIZER or ADMIN. Default guarantees public sign-up creates a Student. |
| users | department | VARCHAR(100) | 100 characters | — | **NULL** | — | Optional department or branch of the user. |
| users | created_at | TIMESTAMPTZ | 8 bytes, microsecond precision | — | NOT NULL | `now()` | Account creation time. |

| venues | location | VARCHAR(255) | 255 characters | — | NOT NULL | — | Building, floor or address of the venue. |

|---|---|---|---|---|---|---|---|

| events | description | TEXT | unbounded | — | NOT NULL | — | Full event details; length varies too much for VARCHAR. |

| registrations | event_id | INTEGER | 4 bytes | FK → events.id (part of composite UK) | NOT NULL | — | Event the student registered for. |
| registrations | student_id | INTEGER | 4 bytes | FK → users.id (part of composite UK) | NOT NULL | — | Student who registered. |
| registrations | status | registration_status (ENUM) | 2 values | — | NOT NULL | `'REGISTERED'` | REGISTERED or CANCELLED (withdrawn or event cancelled). |

### C.5 Table `certificates`

| Table | Column | PostgreSQL type | Size / precision | Key | Nullability | Default | Description and purpose |
|---|---|---|---|---|---|---|---|
| certificates | id | INTEGER | 4 bytes | PK | NOT NULL | identity (auto) | Unique identifier of the certificate. |
| certificates | registration_id | INTEGER | 4 bytes | FK → registrations.id **and** UK | NOT NULL | — | The registration that earned the certificate; unique so there is at most one per registration. |
| certificates | certificate_no | VARCHAR(50) | 50 characters | UK | NOT NULL | — | Human-readable certificate number printed on the PDF. |
| certificates | file_path | VARCHAR(500) | 500 characters | — | NOT NULL | — | Location of the generated PDF in server storage (relative path). |
| certificates | issued_at | TIMESTAMPTZ | 8 bytes, microsecond precision | — | NOT NULL | `now()` | When the certificate was issued. |
| certificates | issued_by | INTEGER | 4 bytes | FK → users.id | NOT NULL | — | The organizer or admin who issued the certificate (audit trail). |

**Column count check:** users 8 + venues 4 + events 13 + registrations 6 + certificates 6 = **37 columns**, matching the ER diagram.

### C.6 Data type choices

| Choice | Reason |
|---|---|
| `INTEGER` identity for IDs | A college project will never approach 2.1 billion rows per table, so INTEGER is sufficient and smaller than BIGINT. Identity columns are the modern PostgreSQL replacement for SERIAL. |
| `VARCHAR(n)` for names, e-mail, ID number, titles, paths | Short strings with a known sensible limit; the limit documents intent and blocks absurdly long input. |
| `TEXT` for `description` and `cancel_reason` | Free-form, variable length; in PostgreSQL TEXT and VARCHAR perform the same, so no artificial limit is needed. |
| `BOOLEAN` for `certificate_eligible` | Exactly two states; clearer and safer than 0/1 integers. |
| `TIMESTAMPTZ` for all timestamps | Stores an absolute moment in time (internally UTC) and converts to the session time zone, which avoids ambiguity if the server and users are in different zones. |
| `INTEGER` for `capacity` and `max_participants` | Whole-number counts. |
| Native `ENUM` types for `role` and both `status` columns | A fixed, small list of values rejected by the database if invalid, and supported directly by Prisma enums (see Section G and the conflict note in Section N). |
| `VARCHAR(255)` for `password_hash` | bcrypt hashes are 60 characters; extra room allows a change of hashing algorithm without altering the table. |

## D. Primary Key Design

| Table | Primary key | Why it is required |
|---|---|---|
| users | `id` | Uniquely identifies a user. It is the target of three foreign keys (`events.organizer_id`, `registrations.student_id`, `certificates.issued_by`) and is carried in the JWT. |
| venues | `id` | Uniquely identifies a venue; target of `events.venue_id`. |
| events | `id` | Uniquely identifies an event; target of `registrations.event_id`. |
| registrations | `id` | Uniquely identifies a registration; target of `certificates.registration_id`. |
| certificates | `id` | Uniquely identifies a certificate; used in download URLs (`/certificates/:id/download`). |

**Design decision:** every table uses a single-column, auto-generated surrogate key. Natural candidates (email, student ID, venue name, certificate number) are kept as **unique keys** instead, because natural values can change or be mistyped, while a surrogate `id` never changes and keeps foreign keys small and fast. For `registrations`, the natural candidate key `(event_id, student_id)` is protected by a composite unique constraint.

## E. Foreign Key Design

| # | Constraint | Referencing table | Referencing column | Referenced table | Referenced column | Relationship purpose |
|---|---|---|---|---|---|---|
| 1 | `fk_events_organizer` | events | organizer_id | users | id | Links each event to the one user who organizes it (**organizes**). |
| 2 | `fk_events_venue` | events | venue_id | venues | id | Assigns each event to exactly one venue (**hosts**). |
| 3 | `fk_registrations_event` | registrations | event_id | events | id | Ties each registration to the event being attended (**receives**). |
| 4 | `fk_registrations_student` | registrations | student_id | users | id | Ties each registration to the student who made it (**makes**). |
| 5 | `fk_certificates_registration` | certificates | registration_id | registrations | id | Ties each certificate to the registration that earned it (**earns**). |
| 6 | `fk_certificates_issuer` | certificates | issued_by | users | id | Records which user issued the certificate (**issues**). |

Six foreign keys implement six relationships; none is omitted. `users` is referenced three times through three different columns, so Prisma uses three named relations (`EventOrganizer`, `StudentRegistrations`, `CertificateIssuer`).

## F. Unique Constraints

| Constraint | Column(s) | Why it is required |
|---|---|---|
| `uq_users_email` | users.email | Each person has one account; e-mail is the login identity. Duplicate sign-ups fail with a clear conflict. |
| `uq_users_student_id_number` | users.student_id_number | One college ID card can belong to only one account, which stops a student from creating several accounts. |
| `uq_venues_name` | venues.name | Prevents two venues with the same name, which would confuse organizers and participants. |
| `uq_registrations_event_student` | registrations(event_id, student_id) | Prevents registering twice for the same event, even when two requests arrive at the same moment. The database is the final safeguard. |
| `uq_certificates_registration_id` | certificates.registration_id | Allows at most one certificate per registration. It also turns the **earns** relationship into one-to-zero-or-one. |
| `uq_certificates_certificate_no` | certificates.certificate_no | Each printed certificate number identifies exactly one certificate, so it can be used for verification. |

## G. CHECK Constraints

### G.1 Constraints enforced by the database

| Rule | How it is enforced | Name |
|---|---|---|
| `users.role` is STUDENT, ORGANIZER or ADMIN | ENUM type `user_role` | `user_role` |
| `venues.capacity` is positive | `CHECK (capacity > 0)` | `chk_venues_capacity_positive` |
| `events.end_time` is later than `events.start_time` | `CHECK (end_time > start_time)` | `chk_events_end_after_start` |
| `events.max_participants` is positive when not NULL | `CHECK (max_participants IS NULL OR max_participants > 0)` | `chk_events_max_participants_positive` |
| `events.status` is a permitted status | ENUM type `event_status` | `event_status` |
| `registrations.status` is REGISTERED or CANCELLED | ENUM type `registration_status` | `registration_status` |
| `users.email` is stored in lower case (additional) | `CHECK (email = lower(email))` | `chk_users_email_lowercase` |

> **Note on ENUM versus CHECK:** the three value-list rules (role and the two status columns) are enforced by native PostgreSQL ENUM types instead of `CHECK (col IN (...))`. An ENUM rejects any other value exactly like a CHECK would, and Prisma maps it to a Prisma `enum`. The equivalent CHECK form, if your instructor prefers it, is:
>
> ```sql
> -- use VARCHAR(20) columns instead of enum types, then:
> ALTER TABLE users         ADD CONSTRAINT chk_users_role
>     CHECK (role IN ('STUDENT','ORGANIZER','ADMIN'));
> ALTER TABLE events        ADD CONSTRAINT chk_events_status
>     CHECK (status IN ('DRAFT','PUBLISHED','CANCELLED','COMPLETED'));
> ALTER TABLE registrations ADD CONSTRAINT chk_registrations_status
>     CHECK (status IN ('REGISTERED','CANCELLED'));
> ```
>
> Using that form means the Prisma schema must use `String` fields instead of enums. See Section N, conflict C1.

### G.2 Rules that need backend (service-layer) validation

The database cannot check these because they depend on other rows, the current time or the logged-in user.

| Rule | Why the database cannot enforce it |
|---|---|
| `registration_deadline` should not be after `start_time` | Intentionally left to Zod/service validation so organizers keep flexibility. |
| A cancelled event must have a `cancel_reason` | Handled when the cancel endpoint runs (not a constraint, so drafts and legacy rows are unaffected). |
| `max_participants` should not exceed the venue `capacity` | Needs a lookup in another table. |
| Active registrations must stay below `max_participants` | Needs a count and a transaction (lock the event row, count `REGISTERED`, then insert). |
| Registration only while the event is PUBLISHED and before the deadline | Depends on the current time and event status. |
| Withdrawal only before the deadline | Depends on the current time. |
| `registrations.student_id` must reference a user with role STUDENT | The role lives in another table. |
| `events.organizer_id` must reference an ORGANIZER or ADMIN | Same reason. |
| `certificates.issued_by` must be an ORGANIZER (owner of the event) or an ADMIN | Depends on the acting user and event ownership. |
| Certificates only for eligible, non-cancelled registrations of finished events | Spans rows and time. |
| Venue cannot host overlapping events | Needs a range comparison against other events (see rule 7 in Section L). |
| Only an ADMIN may change roles | Depends on the authenticated caller. |

## I. Normalization

### I.1 First Normal Form (1NF)

A table is in 1NF when every column holds a single atomic value, there are no repeating groups, and each row is uniquely identifiable.

- Every table has a primary key, so each row is unique.
- All columns are atomic: `name` is one value, `start_time` is one timestamp, `role` holds exactly one role. There are no comma-separated lists such as "event1, event2" and no columns like `event1`, `event2`.
- The many-to-many link between students and events is **not** stored as a list inside `users` or `events`. It is stored as one row per (event, student) pair in `registrations`.

**Result:** all five tables satisfy 1NF.

### I.2 Second Normal Form (2NF)

A table is in 2NF when it is in 1NF and every non-key attribute depends on the **whole** candidate key, not on part of it. Partial dependencies can only occur when a key has more than one column.

- `users`, `venues`, `events` and `certificates` have single-column primary keys (`id`), so a partial dependency is impossible.
- `registrations` has the single-column primary key `id`, but its natural candidate key is the composite `(event_id, student_id)`. Its non-key attributes are:
  - `status`: the state of *this student's* registration for *this event*. It depends on both event and student together.
  - `certificate_eligible`: whether *this student* qualifies for *this event*. It depends on both together.
  - `registered_at`: when *this student* registered for *this event*. It depends on both together.

  None of them can be determined by `event_id` alone or `student_id` alone, so there is no partial dependency.

**Result:** all five tables satisfy 2NF.

### I.3 Third Normal Form (3NF)

A table is in 3NF when it is in 2NF and no non-key attribute depends on another non-key attribute (no transitive dependency). Equivalently, every determinant is a candidate key or the dependent attribute is part of a key.

Functional dependencies (FDs) per table:

| Table | Functional dependencies | Determinants are candidate keys? |
|---|---|---|
| users | `id → name, email, student_id_number, password_hash, role, department, created_at`; `email → id`; `student_id_number → id` | Yes: `id`, `email` and `student_id_number` are all candidate keys. |
| venues | `id → name, location, capacity`; `name → id` | Yes: `id` and `name`. |
| events | `id → title, description, organizer_id, venue_id, start_time, end_time, registration_deadline, max_participants, status, cancel_reason, created_at, updated_at` | Yes: only `id`. |
| registrations | `id → event_id, student_id, status, certificate_eligible, registered_at`; `(event_id, student_id) → id, status, certificate_eligible, registered_at` | Yes: `id` and `(event_id, student_id)`. |
| certificates | `id → registration_id, certificate_no, file_path, issued_at, issued_by`; `registration_id → id`; `certificate_no → id` | Yes: `id`, `registration_id`, `certificate_no`. |

Why transitive dependencies are avoided (the reasoning behind the table split):

- `events.venue_id → venues.location, capacity`: venue details depend on the venue, not on the event, so they live in `venues` and `events` stores only the key `venue_id`. If `location` were copied into `events`, we would have `event.id → venue_id → location`, a transitive dependency and an update anomaly (changing a venue's location would require editing every event).
- `events.organizer_id → users.name, email, department`: the organizer's details are never copied into `events`; they are reached by a join.
- `registrations.student_id → users.name, student_id_number`: student details are never copied into `registrations`.
- `certificates.registration_id → registrations → event/student`: the certificate stores no event title or student name. Those are derived through joins, so they cannot become inconsistent with their source rows.
- `users.department`: it is a plain attribute of the user and no other non-key attribute determines it, so it is not a transitive dependency. (Making it a separate DEPARTMENT table would add an extra entity that the architecture does not include.)

Because every determinant in every table is a candidate key, the schema is in fact also in **Boyce–Codd Normal Form (BCNF)**.

**Result:** all five tables satisfy 3NF. No deliberate denormalization is used.

## J. Index Design

PostgreSQL automatically creates an index for every PRIMARY KEY and UNIQUE constraint, but **not** for foreign key columns. The design therefore adds only the indexes that are missing.

### J.1 Indexes provided automatically (no extra index created)

| Requested index | Already provided by | Note |
|---|---|---|
| users.email | `uq_users_email` | Fast login lookup. |
| users.student_id_number | `uq_users_student_id_number` | Fast lookup by college ID. |
| registrations.event_id | `uq_registrations_event_student` (leading column `event_id`) | Serves "participants of an event" queries, so a separate index would be redundant. |
| certificates.registration_id | `uq_certificates_registration_id` | Serves certificate lookup per registration. |
| certificates.certificate_no | `uq_certificates_certificate_no` | Serves certificate verification by number. |
| venues.name | `uq_venues_name` | Not requested, shown for completeness. |

### J.2 Additional indexes created

| Index | Definition | Purpose |
|---|---|---|
| `idx_events_organizer_id` | `events (organizer_id)` | Organizer dashboard ("my events"). Also speeds up the foreign-key check when a user row is touched. |
| `idx_events_venue_id_start_time` | `events (venue_id, start_time)` | Covers `venue_id` lookups and the **venue clash check**, which searches events at one venue around a time range. Replaces a plain `venue_id` index. |
| `idx_events_status_start_time` | `events (status, start_time)` | The public event list: `WHERE status = 'PUBLISHED' ORDER BY start_time`. Covers both `status` and `start_time` in one index, so separate indexes on each column are unnecessary. |
| `idx_registrations_student_id` | `registrations (student_id)` | "My registrations" for a student. Also speeds up the foreign-key check. |

Indexes that were deliberately **not** created: separate single-column indexes on `events.status` and `events.start_time` (covered by the composite index), `registrations.event_id` and the unique-constraint columns (already indexed), and `certificates.issued_by` (rarely queried; adding it is optional if "certificates issued by me" ever becomes a frequent report). Every extra index slows inserts and updates, so the set is kept small for a prototype.

## K. Referential Integrity

A foreign key guarantees that a child row can never point to a parent row that does not exist. It also decides what happens when someone tries to delete or re-key a parent.

### K.1 Recommended actions

| Foreign key | ON DELETE | ON UPDATE | Reasoning |
|---|---|---|---|
| `events.organizer_id → users.id` | **RESTRICT** | CASCADE | A user who organizes events cannot be deleted; deleting would orphan or destroy event history. |
| `events.venue_id → venues.id` | **RESTRICT** | CASCADE | A venue that has hosted events cannot be deleted; retire it by other means instead. |
| `registrations.event_id → events.id` | **RESTRICT** | CASCADE | An event with registrations cannot be deleted. It is **cancelled** (`status = 'CANCELLED'`), which keeps all participation records. |
| `registrations.student_id → users.id` | **RESTRICT** | CASCADE | A student who has registrations cannot be deleted, so participation history is preserved. |
| `certificates.registration_id → registrations.id` | **RESTRICT** | CASCADE | A registration that has a certificate cannot be deleted; the certificate is proof of participation. |
| `certificates.issued_by → users.id` | **RESTRICT** | CASCADE | A user who issued certificates cannot be deleted, so the audit trail stays intact. |

### K.2 Why no cascading deletes

`ON DELETE CASCADE` is **not used anywhere**. A single accidental delete of a user, event or registration would silently wipe registrations and certificates, which are the most important records in the system. `RESTRICT` makes the database refuse the delete instead, forcing the application to use status changes (cancel an event, withdraw a registration) rather than removing history. `SET NULL` is not possible either, because all foreign key columns are NOT NULL (for example `issued_by` must always name an issuer).

`ON UPDATE CASCADE` is harmless: primary keys are generated by the database and never edited, but if one were ever changed, the references would follow automatically. It also matches Prisma's default for required relations.

### K.3 Operational consequence

The schema has no "inactive user" column (the five-table design fixes the column list), so ordinary users are **not deleted**. If an account must be disabled, an administrator can change its role and the application can block login; hard deletion is only possible for accounts with no events, registrations or issued certificates. A venue that was never used can be deleted; a used one cannot.

## L. Business Rules

| # | Business rule | Enforced by | How |
|---|---|---|---|
| 1 | Public registration always creates STUDENT accounts. | **Both** | Database: `role` defaults to `STUDENT`. Backend: the register endpoint's Zod schema rejects or strips any `role` field and never sets one. |
| 2 | Only an authorized ADMIN can assign ORGANIZER or ADMIN roles. | **Backend/service validation** | The database cannot know who is acting. Only `PATCH /users/:id/role`, protected by JWT and an ADMIN check, changes `role`. The database only guarantees the value is one of the three valid roles. |
| 3 | College email and student ID must be unique. | **Both** | Database: `uq_users_email` and `uq_users_student_id_number` (plus lower-case check on e-mail). Backend: checks college e-mail domain and ID format, and returns a friendly `409 Conflict`. |
| 4 | Students cannot register twice for the same event. | **Both** | Database: `uq_registrations_event_student`. Backend: checks first and handles the unique-violation error; a withdrawn student re-registering reuses the existing row (sets status back to REGISTERED). |
| 5 | Event participant limits must be enforced. | **Backend/service validation** | Inside a transaction the service locks the event row, counts `REGISTERED` rows and rejects the request if the count has reached `max_participants`. When `max_participants` is NULL, no limit applies. The database only guarantees the limit, if present, is positive. |
| 6 | Students can withdraw before the registration deadline while registration remains open. | **Backend/service validation** | The service allows withdrawal only if the event is PUBLISHED, `now() < registration_deadline` and the registration is REGISTERED, then sets its status to CANCELLED. The database only guarantees `status` is a valid value. |
| 7 | A venue cannot host overlapping events. | **Backend/service validation** | On create/update the service rejects an event if another non-cancelled event at the same venue satisfies `existing.start_time < new.end_time AND existing.end_time > new.start_time`. The index `idx_events_venue_id_start_time` supports this query. (PostgreSQL could enforce it with an exclusion constraint, but that is intentionally left out to keep the prototype simple and matches the ER design.) |
| 8 | Certificates are issued only to eligible participants with valid, non-cancelled registrations. | **Backend/service validation** | The service issues certificates only where `certificate_eligible = true` and registration `status = 'REGISTERED'`, for events that have finished. The database stores the flag and status but cannot evaluate this rule. |
| 9 | One registration can have at most one certificate. | **Both** | Database: `uq_certificates_registration_id`. Backend: skips registrations that already have a certificate, so reissuing does not fail. |
| 10 | `issued_by` records the user who issued a certificate. | **Both** | Database: `issued_by` is NOT NULL with foreign key `fk_certificates_issuer`. Backend: fills it from the authenticated user (JWT), never from request input. |

**Summary:** rules 1, 3, 4, 9 and 10 are enforced by both layers; rules 2, 5, 6, 7 and 8 need backend logic.

### M.1 Differences between PostgreSQL and Prisma representations

| Topic | PostgreSQL (SQL script) | Prisma schema | Effect |
|---|---|---|---|
| Table names | `users`, `events`, … | Models `User`, `Event`, … with `@@map("users")` | Same tables; Prisma uses singular PascalCase model names. |
| Enums | `CREATE TYPE user_role AS ENUM (...)` | `enum UserRole { ... } @@map("user_role")` | Identical native enum types. |
| Auto IDs | `GENERATED BY DEFAULT AS IDENTITY` | `@default(autoincrement())` | Prisma's own migrations would create `SERIAL` columns instead of identity columns. Both behave the same for the application. |
| Timestamps | `TIMESTAMPTZ` | `DateTime @db.Timestamptz(6)` | Identical. Without `@db.Timestamptz` Prisma would use a timezone-less timestamp. |
| `updated_at` | `DEFAULT now()` plus trigger `trg_events_set_updated_at` | `@default(now()) @updatedAt` | Prisma sets the value in the client; the trigger also covers manual SQL updates. |
| CHECK constraints | `chk_venues_capacity_positive`, `chk_events_end_after_start`, `chk_events_max_participants_positive`, `chk_users_email_lowercase` | **Not supported** by Prisma schema language | Must be added through SQL (see M.2). Zod validation in the API should mirror them. |
| Constraint and index names | Explicit | Same names via `map:` arguments | Prisma will not rename or duplicate constraints. |
| Foreign key actions | `ON DELETE RESTRICT ON UPDATE CASCADE` | `onDelete: Restrict, onUpdate: Cascade` | Identical. |
| One-to-zero-or-one | `UNIQUE (registration_id)` | `registration_id Int @unique` and `certificate Certificate?` on the other side | Identical meaning. |
| Multiple relations to `users` | Three different FK columns | Three named relations: `EventOrganizer`, `StudentRegistrations`, `CertificateIssuer` | Required by Prisma when two models are linked more than once or ambiguity exists. |
| Field names | snake_case columns | Same snake_case field names | Kept identical to the ER diagram for traceability. A camelCase style with `@map` is possible but not used. |

### M.2 If you create the database with Prisma Migrate

Run `prisma migrate dev --create-only`, then append the following to the generated migration SQL before applying it, so the database also gets the constraints and trigger Prisma cannot describe:

```sql
ALTER TABLE users  ADD CONSTRAINT chk_users_email_lowercase
    CHECK (email = lower(email));
ALTER TABLE venues ADD CONSTRAINT chk_venues_capacity_positive
    CHECK (capacity > 0);
ALTER TABLE events ADD CONSTRAINT chk_events_end_after_start
    CHECK (end_time > start_time);
ALTER TABLE events ADD CONSTRAINT chk_events_max_participants_positive
    CHECK (max_participants IS NULL OR max_participants > 0);

CREATE OR REPLACE FUNCTION set_updated_at() RETURNS trigger AS $$
BEGIN
    NEW.updated_at = now();
    RETURN NEW;
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER trg_events_set_updated_at
    BEFORE UPDATE ON events
    FOR EACH ROW EXECUTE FUNCTION set_updated_at();
```

Use **either** the SQL script **or** Prisma Migrate to create the database, not both on the same database.

## N. Consistency Review: Conflicts and Notes

Per the project instructions, these differences between the architecture, the ER diagram and this schema are listed openly rather than changed silently.

| # | Item | Finding | Resolution in this design |
|---|---|---|---|
| C1 | **CHECK versus ENUM** for role/status | The requirement lists CHECK constraints for `role` and both `status` columns, while Prisma enums require native PostgreSQL enum types. A VARCHAR + CHECK column cannot be used with a Prisma `enum`. | Native ENUM types are used. They give the same database-level protection and keep Prisma consistent. The equivalent CHECK form is documented in Section G.1 if you prefer it (then use `String` in Prisma). |
| C2 | Student ID column name | The earlier architecture draft (v1.0) called it `college_id`; ER diagram and v1.1 use `student_id_number`. | `student_id_number` is used everywhere. Update any remaining v1.0 text and API examples. |
| C3 | `department` nullability | The v1.0 draft did not mark `department` nullable; v1.1 and the ER diagram do. | Nullable, as in v1.1. |
| C4 | Index column order | Architecture lists an index on `events(start_time, status)`. | The schema uses `events(status, start_time)`. For `WHERE status = 'PUBLISHED' ORDER BY start_time`, putting the equality column first lets one index handle filtering and ordering. Same columns, better order. |
| C5 | Status values | The ER diagram lists `status` without values. | Event: DRAFT, PUBLISHED, CANCELLED, COMPLETED. Registration: REGISTERED, CANCELLED. |
| C6 | Role of referenced users | The database cannot guarantee that `organizer_id` and `issued_by` point to ORGANIZER/ADMIN users or that `student_id` points to a STUDENT. | Enforced in the service layer (Section G.2). Adding triggers was rejected to avoid unnecessary complexity. |
| C7 | No deactivation column | With exactly the specified columns and RESTRICT rules, users with history cannot be hard-deleted. | Accepted as intentional; accounts are disabled by role/login control, not deletion (Section K.3). |
| C8 | Venue overlap | Architecture assigns this to backend/service logic. | Kept in the backend. An optional PostgreSQL exclusion constraint exists but is not used. |
| C9 | Withdrawal wording | The API uses `DELETE /events/:id/registrations/me`, but the schema keeps the row. | The endpoint sets `registrations.status = 'CANCELLED'`; it does not delete the row. This preserves history and the unique constraint. |
| C10 | `certificate_eligible` after withdrawal | A withdrawn (CANCELLED) registration could still have `certificate_eligible = true`. | Certificate issuance requires `status = 'REGISTERED'` as well (rule 8), so stale flags cause no harm. |

No unauthorized entity was added: the design has no ROLE, PERMISSION, LOGIN or EVENT_SESSION table, and the technology stack is unchanged.
