## 1. Introduction

A data dictionary is the official reference that describes every table and column of a database: what it means, its data type, whether it may be empty, and which rules apply to it. This document describes the database of the College Event Management System, a web application where students find and register for college events, organizers create and manage events, and administrators manage users and roles. The system also records registrations and issues participation certificates.

The database has **exactly five tables** and **37 columns**. All names, data types, lengths, defaults and constraint names in this document are taken unchanged from the approved SQL and Prisma schemas. No table, column or relationship has been added or renamed.

### 1.1 Conventions used

| Term | Meaning |
|---|---|
| PK | Primary Key: uniquely identifies each row |
| FK | Foreign Key: refers to the primary key of another table |
| UK | Unique Key: no two rows may hold the same value |
| NOT NULL | The column must always contain a value |
| `TIMESTAMPTZ` | Date and time that includes a time zone; stored as an absolute moment (UTC) |
| ENUM | A PostgreSQL type that accepts only a fixed list of values |
| Identity | An automatically generated integer (`GENERATED BY DEFAULT AS IDENTITY`) |

Constraint names follow the pattern `pk_`, `fk_`, `uq_`, `chk_`, `idx_` followed by table and column, for example `uq_users_email`.

### 1.2 Distinguishing similar identifiers

| Name | Table | Meaning |
|---|---|---|
| `users.id` | users | Internal system number of an account. Generated automatically; never shown to the user as an ID card number. |
| `users.student_id_number` | users | The student's **college ID card number** (for example `21CS045`). Entered at sign-up, unique, and printed nowhere else in the system by default. |
| `registrations.student_id` | registrations | A **foreign key** holding the `users.id` of the student who made the registration. Despite its name it is *not* the college ID card number. |
| `registrations.id` | registrations | Internal number of one registration (one student for one event). |
| `certificates.certificate_no` | certificates | The printed certificate number, separate from the internal `certificates.id`. |

## 2. Entity-wise Data Dictionary

Each table below lists every column. "Size / Length" for `INTEGER` is the storage size (4 bytes, range −2,147,483,648 to 2,147,483,647); for `TIMESTAMPTZ` it is 8 bytes with microsecond precision.

### 2.4 REGISTRATIONS (table `registrations`)

**Purpose:** records that one student has registered for one event. Each row links a student to an event and tracks whether the registration is still active and whether the student qualifies for a certificate.

| Attribute Name | Description | Data Type | Size / Length | Key Type | NULL Allowed | Default Value | Constraints | Example Value |
|---|---|---|---|---|---|---|---|---|
| `id` | Automatically generated identifier of the registration. Referenced by `certificates.registration_id`. | INTEGER | 4 bytes | PK | No | Identity (auto-generated) | `pk_registrations` PRIMARY KEY, NOT NULL | `45` |
| `event_id` | The event the student registered for. Refers to `events.id`. Together with `student_id` it forms a composite unique key. | INTEGER | 4 bytes | FK → `events.id` | No | None | NOT NULL; `fk_registrations_event`; part of `uq_registrations_event_student` | `12` |
| `student_id` | The student who registered. Refers to `users.id` (not the college ID card number). That user must hold the STUDENT role (checked by the backend). | INTEGER | 4 bytes | FK → `users.id` | No | None | NOT NULL; `fk_registrations_student`; part of `uq_registrations_event_student`; indexed by `idx_registrations_student_id` | `101` |
| `status` | Whether the registration is active or has been cancelled (see Section 3.3). | `registration_status` (ENUM) | 2 allowed values (stored in 4 bytes) | None | No | `'REGISTERED'` | NOT NULL; only `REGISTERED`, `CANCELLED` accepted | `REGISTERED` |
| `certificate_eligible` | True when the organizer has marked the participant as qualifying for a certificate (for example after attending). It is a flag only; it does not issue anything. | BOOLEAN | 1 byte | None | No | `false` | NOT NULL | `true` |
| `registered_at` | Moment the student registered, set automatically. | TIMESTAMPTZ | 8 bytes | None | No | `now()` | NOT NULL | `2026-11-15 18:42:10+05:30` |

**Composite unique constraint:** `uq_registrations_event_student` UNIQUE (`event_id`, `student_id`).
Each *combination* of event and student may occur only once. The same student can register for many different events, and one event can have many students, but the same student cannot hold two registration rows for the same event. This is why a student who withdraws and registers again reuses the existing row (status returns to `REGISTERED`) instead of creating a second one.

### 2.5 CERTIFICATES (table `certificates`)

**Purpose:** records each participation certificate issued, including its number, the stored PDF file and the person who issued it.

| Attribute Name | Description | Data Type | Size / Length | Key Type | NULL Allowed | Default Value | Constraints | Example Value |
|---|---|---|---|---|---|---|---|---|
| `id` | Automatically generated identifier of the certificate, used in download links. | INTEGER | 4 bytes | PK | No | Identity (auto-generated) | `pk_certificates` PRIMARY KEY, NOT NULL | `9` |
| `registration_id` | The registration for which the certificate was issued. Refers to `registrations.id`. Being both a foreign key and unique means each registration can have **at most one** certificate. | INTEGER | 4 bytes | FK, UK → `registrations.id` | No | None | NOT NULL; `fk_certificates_registration`; `uq_certificates_registration_id` UNIQUE | `45` |
| `certificate_no` | Human-readable number printed on the certificate, used to verify it. | VARCHAR | 50 | UK | No | None | NOT NULL; `uq_certificates_certificate_no` UNIQUE | `CERT-2026-AI-0045` |
| `file_path` | Location of the generated PDF in server storage. Stored as a relative path, not a web address. | VARCHAR | 500 | None | No | None | NOT NULL | `certificates/2026/CERT-2026-AI-0045.pdf` |
| `issued_at` | Moment the certificate was issued, set automatically. | TIMESTAMPTZ | 8 bytes | None | No | `now()` | NOT NULL | `2026-12-06 11:30:00+05:30` |
| `issued_by` | The user (organizer or administrator) who issued the certificate. Refers to `users.id`. Filled by the backend from the logged-in user, never from request input. | INTEGER | 4 bytes | FK → `users.id` | No | None | NOT NULL; `fk_certificates_issuer` | `7` |

**Uniqueness of `registration_id`:** a plain foreign key would allow many certificates to point at one registration (one-to-many). Adding `UNIQUE` restricts it to one-to-zero-or-one: a registration has no certificate until one is issued, and never more than one afterwards.

## 3. Enumerated Values

Three columns use PostgreSQL ENUM types, so the database itself rejects any other value.

### 3.1 `user_role` (column `users.role`)

| Value | Meaning | When it is used |
|---|---|---|
| `STUDENT` | A student who can browse events, register, withdraw and download own certificates. | Assigned automatically to every account created through public registration. It is the default. |
| `ORGANIZER` | A person who can create and manage their own events, view participants, mark certificate eligibility and issue certificates. | Assigned only by an administrator to an existing account. |
| `ADMIN` | An administrator who can manage users and roles and venues, and oversee all events. | Assigned only by an existing administrator; the first administrator is created by a database seed script. |

### 3.2 `event_status` (column `events.status`)

| Value | Meaning | When it is used |
|---|---|---|
| `DRAFT` | Event is being prepared and is not visible to students. | Default when an organizer creates an event. |
| `PUBLISHED` | Event is visible and open for registration until the deadline (and until any participant limit is reached). | After the organizer publishes the event. |
| `CANCELLED` | Event will not take place; `cancel_reason` explains why. | When an organizer or administrator cancels a draft or published event. |
| `COMPLETED` | Event has finished. Certificates can be issued only for such events. | Once the event end time has passed. |

### 3.3 `registration_status` (column `registrations.status`)

| Value | Meaning | When it is used |
|---|---|---|
| `REGISTERED` | The student holds an active place in the event. Counts toward the participant limit. | Default when a student registers; also when a withdrawn student registers again. |
| `CANCELLED` | The registration is no longer active (the student withdrew before the deadline, or the event was cancelled). The row is kept for history. | When a student withdraws or an event is cancelled. |

## 4. Relationships and Referential Integrity

Six foreign keys implement the six relationships of the ER diagram. Every foreign key column is NOT NULL, so the "one" side is always mandatory (for example, an event always has exactly one organizer and one venue).

| # | Foreign key (constraint) | Cardinality | Purpose |
|---|---|---|---|
| 1 | `events.organizer_id` → `users.id` (`fk_events_organizer`) | One user organizes 0..N events; each event has exactly 1 organizer | Records who is responsible for each event and lets an organizer see "my events". |
| 2 | `events.venue_id` → `venues.id` (`fk_events_venue`) | One venue hosts 0..N events; each event has exactly 1 venue | Assigns the event to a place and supports the venue-clash check. |
| 3 | `registrations.event_id` → `events.id` (`fk_registrations_event`) | One event receives 0..N registrations; each registration belongs to exactly 1 event | Builds each event's participant list. |
| 4 | `registrations.student_id` → `users.id` (`fk_registrations_student`) | One user makes 0..N registrations; each registration belongs to exactly 1 student | Builds each student's "my registrations" list. |
| 5 | `certificates.registration_id` → `registrations.id` (`fk_certificates_registration`) | One registration earns 0..1 certificate; each certificate belongs to exactly 1 registration | Proves participation; the unique constraint prevents duplicates. |
| 6 | `certificates.issued_by` → `users.id` (`fk_certificates_issuer`) | One user issues 0..N certificates; each certificate records exactly 1 issuer | Audit trail of who issued each certificate. |

**What referential integrity guarantees:** a child row can never refer to a parent that does not exist. For example, a registration cannot be created for an event that does not exist, and an event cannot be deleted while registrations still refer to it. Every foreign key uses `ON DELETE RESTRICT` and `ON UPDATE CASCADE` (summarised in Section 6.4), so important records are never removed automatically.

## 5. Business Rules

| # | Business rule | Relevant attributes | Enforced by | Explanation |
|---|---|---|---|---|
| 1 | Public registration creates STUDENT accounts by default. | `users.role` | **Both** | Database: default `'STUDENT'`. Backend: the sign-up validation (Zod) rejects or ignores any `role` value sent by the client. |
| 2 | Only authorized administrators can assign ORGANIZER or ADMIN roles. | `users.role` | **Backend** | The database cannot know who is making a change. Only an administrator-protected endpoint changes roles; the database merely ensures the value is one of the three valid roles. |
| 3 | User e-mail addresses and student ID numbers must be unique. | `users.email`, `users.student_id_number` | **Both** | Database: `uq_users_email`, `uq_users_student_id_number`, and the lower-case e-mail check. Backend: validates college e-mail domain and ID format and returns a clear "already exists" message. |
| 4 | A student cannot register for the same event more than once. | `registrations.event_id`, `registrations.student_id` | **Both** | Database: `uq_registrations_event_student`. Backend: checks first and reuses the existing row when a withdrawn student registers again. |
| 5 | Event participant limits must be enforced. | `events.max_participants`, `registrations.status` | **Backend** | In one transaction the service counts registrations with status `REGISTERED` and refuses a new one when the limit is reached. NULL means no limit. The database only ensures the limit, when given, is positive. |
| 6 | Students can withdraw before the registration deadline, subject to the event's registration rules. | `events.registration_deadline`, `events.status`, `registrations.status` | **Backend** | Withdrawal is allowed only while the event is `PUBLISHED`, the deadline has not passed and the registration is `REGISTERED`. The row is kept and its status becomes `CANCELLED`. |
| 7 | A venue cannot host overlapping events. | `events.venue_id`, `events.start_time`, `events.end_time` | **Backend** | The service rejects an event if another non-cancelled event at the same venue overlaps its time range. The database only ensures that `end_time` is after `start_time`. |
| 8 | Certificates can only be issued to eligible participants with valid, non-cancelled registrations. | `registrations.certificate_eligible`, `registrations.status`, `events.status` | **Backend** | The service issues certificates only where `certificate_eligible` is true, the registration status is `REGISTERED` and the event is completed. |
| 9 | Each registration can have at most one certificate. | `certificates.registration_id` | **Both** | Database: `uq_certificates_registration_id`. Backend: skips registrations that already have a certificate. |
| 10 | The `issued_by` field records the user responsible for issuing a certificate. | `certificates.issued_by` | **Both** | Database: NOT NULL foreign key to `users.id`. Backend: fills it from the authenticated user, never from the request. |

### 6.4 Referential Integrity Summary

| Foreign key | Referenced table | ON DELETE | ON UPDATE | Effect |
|---|---|---|---|---|
| `events.organizer_id` | users | RESTRICT | CASCADE | A user who organizes events cannot be deleted. |
| `events.venue_id` | venues | RESTRICT | CASCADE | A venue that hosted events cannot be deleted. |
| `registrations.event_id` | events | RESTRICT | CASCADE | An event with registrations cannot be deleted; it is cancelled instead. |
| `registrations.student_id` | users | RESTRICT | CASCADE | A student with registrations cannot be deleted. |
| `certificates.registration_id` | registrations | RESTRICT | CASCADE | A registration that has a certificate cannot be deleted. |
| `certificates.issued_by` | users | RESTRICT | CASCADE | A user who issued certificates cannot be deleted. |

No foreign key uses cascading deletion, so registrations and certificates can never be wiped by deleting a parent record. `ON UPDATE CASCADE` is harmless because identifiers are generated automatically and never edited.

### 6.6 Assumptions and Design Notes

**Rules that the database schema alone cannot guarantee** (they depend on other rows, the current time, or the logged-in user, so the backend must enforce them):
- Roles of referenced users: `events.organizer_id` should belong to an ORGANIZER or ADMIN, `registrations.student_id` to a STUDENT, and `certificates.issued_by` to an ORGANIZER or ADMIN.
- Participant limit, withdrawal deadline, venue overlap, certificate eligibility, and administrator-only role changes (rules 2, 5, 6, 7, 8).
- A cancelled event should carry a `cancel_reason`, and `max_participants` should not exceed the venue `capacity`.
- A registration marked CANCELLED may still have `certificate_eligible = true`; the issuing rule requires status `REGISTERED`, so this causes no harm.

**Design notes**
- Event date and time are stored directly in `events` (one start and end time); there is no session table.
- Role is a column of `users`; there are no separate role, permission or login tables.
- Withdrawal changes `registrations.status` to `CANCELLED`; the row is not deleted, which preserves history and keeps the unique constraint valid.
- Because of `ON DELETE RESTRICT` and the fixed column list, ordinary users are disabled by role and login control, not deleted.
- Example values are illustrative only; time zone `+05:30` is used because timestamps are stored with time zone.
